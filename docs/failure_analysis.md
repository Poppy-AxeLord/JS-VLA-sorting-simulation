# 失败分析方法论 —— 工业分拣 VLA 评测

> 文档定位：本文讲清楚我们**为什么把失败分成这 5 大类、每一类怎么判定、如何从一次失败分析得出可执行的优化建议、以及失败分析如何驱动整个产品迭代**。对应代码：`src/evaluation/failure_analysis.py`、`src/evaluation/recommendation.py`，以及 `src/sorting/engine.py` 里的失败注入模型。

---

## 一、核心理念：失败是一等公民

绝大多数算法 Demo 把失败藏起来——调参数把成功率刷上去，演示时只放成功的片段。**我们反过来，把失败当成最有价值的产品资产。**

理由很简单：在工业落地决策里，决策者真正想知道的不是"它能成功多少次"，而是"**它会怎么失败、失败能不能修、修了能涨多少**"。一个永远 100% 成功的 Demo 反而最不可信。所以我们刻意用概率模型注入真实分布的失败（见第五节），让失败可观测、可归因、可优化。

---

## 二、为什么是这 5 大类（分类方法论）

失败分类的设计原则是：**沿着"指令进来 → 系统处理 → 物理执行"的因果链切分，让每一类失败都对应一个可独立优化的环节，且类与类之间互斥、整体上穷尽（MECE）。**

VLA 分拣的处理链路天然分为四个认知-行动环节，再加上环境扰动，正好是 5 类：

```
指令 + 场景
   │
   ├─①感知（看）——— 我看到了什么？———————→ perception 感知类失败
   │
   ├─②理解（懂）——— 指令要我做什么？————→ understanding 理解类失败
   │
   ├─③规划（想）——— 按什么顺序/路径做？——→ planning 规划类失败
   │
   ├─④执行（做）——— 抓得起放得下吗？————→ execution 执行类失败
   │
   └─⑤环境（变）——— 外部发生了意外吗？——→ environment 环境类失败
```

这套切分的好处：**每一类失败都唯一对应一个技术模块和一个优化抓手**——感知类对应相机/视觉，理解类对应 VLA 语言解析，规划类对应 planner，执行类对应 robot/strategies，环境类对应仿真鲁棒性。归因即定位，定位即行动。

### 5 大类 + 子类 + 统一配色（全项目一致）

| 大类 key | 大类中文 | 子类 | 配色 |
|---|---|---|---|
| perception | 感知类失败 | 识别错误 / 定位不准 / 遮挡看不见 / 光照角度问题 | `#5B8FF9` |
| understanding | 理解类失败 | 指令理解错误 / 漏理解约束 / 歧义处理失败 | `#5AD8A6` |
| planning | 规划类失败 | 路径不合理 / 分拣顺序错误 / 优先级处理错误 | `#F6BD16` |
| execution | 执行类失败 | 抓取失败(滑落) / 放置失败(掉落) / 碰撞导致失败 | `#E8684A` |
| environment | 环境类失败 | 物体意外移动 / 障碍物出现 / 仿真物理异常 | `#9270CA` |

> 存储约定：`failure_category` 存大类中文（"感知类失败"等），`failure_subtype` 存子类中文。配色全项目统一（看板饼图/堆叠图/趋势图共用），保证视觉语言一致，决策者一眼识类。

## 三、判定逻辑：一次失败如何被归到某一类

判定遵循**"沿因果链就近归因"**原则——失败在哪个环节最早被引入，就归到哪一类，避免一果多因导致归类混乱。具体判定优先级：

1. **环境类优先排除**：若是物体意外移动/障碍物出现/仿真物理异常等外部扰动导致，归 environment（因为这不是模型本身的能力问题，需单独看待）。
2. **感知是源头**：若识别/定位本身就错了（看错零件、看不到被遮挡的零件、光照导致误判），归 perception。错误的输入会污染后续所有环节，必须最先归因。
3. **理解次之**：感知正确但对指令的解读错了（把"金属零件"理解成了"银色零件"、漏掉了"只放 A 区"的约束、模糊指令处理失败），归 understanding。
4. **规划再次**：感知和理解都对，但执行顺序/路径/优先级安排不合理（先抓了易碎件却被后续动作撞掉、优先级指令没按序），归 planning。
5. **执行兜底**：前面都对，纯粹是物理执行没成（抓取滑落、放置掉落、运动中碰撞），归 execution。

> 工程实现：在 `engine.py` 的失败注入模型里，每类失败被注入时直接打上 `failure_category` 和 `failure_subtype`，并写入 `failure_reason`（中文可读原因）。真实接入 CV/VLA 后，这套判定逻辑可由各模块的置信度和真值对比自动推断。

### 两套归因逻辑：注入时「就近归因」 vs 展示时「严重度优先」

上面第 1~5 条讲的是**单步失败发生时的「就近归因」**——沿因果链把某一步归到「最早引入错误」的环节（`engine._inject_failure`）。但一个任务往往有多步、可能横跨多类失败，**对外只报一个「任务级失败归因」时**，就需要第二套逻辑：

- **注入时·就近归因**（`_inject_failure`）：决定**每一步**失败的 `failure_category`，是 MECE 分类的事实基础，保证「每步归对类」。
- **展示时·严重度优先**（`engine._summarize`）：当一个任务并存多类失败时，任务级归因取**严重度最高**的一类作代表——`理解 > 规划 > 感知 > 执行 > 环境`。理由是理解类错误最难自动救回、返工成本最高，**最该优先排期治理**；把它顶到任务级归因，能让优化建议聚焦「治本」而非「治标」。

> 二者不矛盾也不重复：就近归因回答「这一步为什么错」，严重度优先回答「这个任务多类都错时先报/先治哪一类」。分层分析（按环节看占比）用前者，单任务卡片与优先级排序用后者。

## 四、从失败分析到可执行优化建议（闭环举例）

这是失败分析最有产品价值的部分。`failure_analysis.py` 产出聚合结果，`recommendation.py` 把它翻译成**带数据支撑、带预期收益、按"高影响低成本"排序的可执行建议**。下面是一个完整闭环示例：

### 闭环示例：困难难度成功率上不去

**第 1 步 —— 观测（failure_analysis 输出）**
```
category_distribution（困难难度）:
  感知类失败  40%  ← 其中"遮挡看不见" 22%、"识别错误" 12%
  执行类失败  25%  ← 其中"放置失败(掉落)" 15%（集中在易碎大件）
  理解类失败  15%
  规划类失败  12%
  环境类失败   8%
对照核心指标：漏拣率偏高、易碎件 grasp_success_rate 偏低
```

**第 2 步 —— 归因（人 + recommendation 推理）**
- 感知类占比最高，且主因是"遮挡看不见"（22%）。当前只有俯视单相机，被遮挡零件直接漏掉 → 漏拣率高。
- 执行类第二，集中在易碎大件"放置掉落"。抓取姿态没考虑零件易碎性和重心。

**第 3 步 —— 生成建议（recommendation.py 输出，按高影响低成本排序）**

| 优先级 | 标题 | 问题(evidence) | 方案(solution) | 预期收益 | 影响/成本 |
|---|---|---|---|---|---|
| 高 | 引入多视角融合 | 感知失败占 40%，其中遮挡 22% | 增加侧视相机，俯视+侧视融合消除遮挡盲区 | 成功率 +6~8pct | 高影响 / 中成本 |
| 高 | 易碎件抓取风险预判 | 执行失败 25%，放置掉落集中在易碎大件 | 启用世界模型 `assess_grasp_risk`，抓取前调整姿态/降速 | 成功率 +4~6pct | 高影响 / 低成本 |
| 中 | 模糊指令解析增强 | 理解失败 15%，"大左小右"类歧义处理失败 | 强化 rule_based 的相对约束解析 | 误拣率 -3pct | 中影响 / 低成本 |

**第 4 步 —— 执行 + 验证（迭代）**
- 先做"高影响低成本"的世界模型（v3 已验证：0.74→0.83）。
- 再做多视角融合（v4 规划，预期困难难度 +6~8pct）。
- 每做完一项，重跑 benchmark，看北极星指标涨没涨、对应那类失败占比降没降。**涨了且降了 → 建议有效；没涨 → 归因错误，回到第 2 步重新分析。**

> 这就是完整闭环：**观测失败分布 → 归因到环节 → 生成带预期收益的建议 → 按 ROI 执行 → 重测验证 → 回到观测**。这个闭环本身，就是本产品最核心的方法论资产。

## 五、失败注入模型（为什么这样设计，关键产品决策）

产品验证阶段我们不需要真实 CV/VLA 的算力，但需要"统计上真实"的失败分布来让评测和归因有意义。`engine.py` 的失败注入模型按以下逻辑用概率注入 5 类失败（用 `random`，benchmark 支持 seed 复现，demo 用 `random.seed(42)` 确定性生成）：

| 注入条件 | 抬升的失败类型 | 现实依据 |
|---|---|---|
| 遮挡（困难难度 occlusion=true） | ↑ 感知类（遮挡看不见） | 单相机被遮挡是真实产线最常见盲区 |
| 相似物（如螺丝/螺母同银色） | ↑ 感知类（识别错误） | 同色同材质零件最易混淆 |
| 易碎 + 大件（芯片/PCB/显示屏） | ↑ 执行类（放置失败掉落） | 重心高、易碎，放置最易出事 |
| 模糊指令（"大左小右"） | ↑ 理解类（歧义处理失败） | 相对/模糊语义是 VLA 理解软肋 |
| 多零件（任务零件数多） | ↑ 规划类（顺序/路径错误） | 组合越多，规划越易出错 |
| 随机扰动 | ↑ 环境类（物体意外移动等） | 模拟不可控的外部噪声 |

**基线校准**：rule_based 在 简单/中等/困难 的任务成功率约 **0.85 / 0.70 / 0.55**；启用更优 strategy 或 world_model 时整体提升 8~15 个百分点。这组数字不是拍脑袋——它让 v1→v2→v3（约 0.62→0.74→0.83）的提升曲线既有挑战性又可达成，从而真实演示"失败归因驱动优化"的全过程。

> 产品决策记录：**失败注入是手段不是目的。** 它的唯一使命是让"失败分析 → 优化建议 → 验证提升"这条产品方法论在零真实算力成本下完整跑通。一旦接入真实 CV/VLA，注入模型即可被真实失败信号替换，而上层的分类体系、判定逻辑、闭环方法论完全复用——这正是模块化设计的价值。

## 六、失败分析驱动迭代的方法论总结

1. **失败先分类，再谈优化。** 没有归因的优化是盲目调参；有归因的优化是精准打击。
2. **沿因果链就近归因，保证 MECE。** 5 大类互斥穷尽，每类唯一对应一个优化抓手。
3. **失败分布 + 核心指标交叉读。** 失败占比告诉你"哪类多"，误拣/漏拣率告诉你"哪类痛"，两者结合定优先级。
4. **建议必须带数据和预期收益。** "感知失败占 40%，建议多视角融合，预期 +6~8pct"——可执行、可验证、可问责。
5. **按高影响低成本排序。** 先摘低垂的果子（如世界模型，低成本高收益），再啃硬骨头（如多视角融合）。
6. **闭环验证，错了就回炉。** 优化后重测，涨了证明归因对，没涨就回到失败分析重新归因。

> 一句话：**失败分析不是给系统"挑毛病"，而是给迭代"指方向"。它把"系统不好用"这种模糊抱怨，变成了"感知类遮挡失败占 22%，做多视角融合预期涨 6~8pct"这种可以立刻排期执行的工程任务。**
